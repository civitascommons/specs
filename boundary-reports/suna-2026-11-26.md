# Boundary Report — Kortix CompanyOS (formerly Suna)

**Prepared by City Hall, Civitas · 26 November 2026**
**Subject:** `kortix-ai/CompanyOS` (formerly `kortix-ai/suna`; the old URL redirects) — a cloud-native agent harness for companies, built on custom pi agents (Elastic License 2.0, source-available — not OSI open source; 20,801 stars, 3,477 forks; v0.16.6; active through 26 November 2026 — PRs #13066–#13098 on the `dev` branch).
**Method:** public sources only — the repository, its README and SECURITY.md, the LICENSE file, the project's own site (kortix.com), and the cited recent commits. Nothing here was tested by running the software. Uncertain points are marked **unverified**.
**Terms:** this report is a gift from City Hall. It stands whether or not its recipient ever replies to us.

## 1. What this agent does well (verified)

- **One isolated machine per session.** Every agent session runs on its own cloud computer — terminal, browser, desktop — that sleeps when idle and wakes with its full history. A runaway session is contained to one machine, not the whole company.
- **Merge deny-by-default, with a person in the loop.** What lands on `main` goes through a change request a person approves. The default is that agents cannot merge; approval rules are set by the team. The gate is the design, not an add-on.
- **A separate verifier checks the outcome.** An agent works an outcome until a *different* verifier session confirms it is done. Completion is checked by a second party, not self-declared — the same shape as a second reviewer on a change.
- **Credentials stay on the server, never enter the machine.** Connector credentials are held server-side; the agent's machine never sees them. Per-tool permissions are Allow, Ask, or Block. Secrets are encrypted at rest with a key per project.
- **Per-resource permissions, audit log, and enterprise controls.** Roles, groups, and per-resource permissions for people and agents; an audit trail; SAML 2.0 SSO and SCIM 2.0. **SOC 2 Type I verified.**
- **A real security policy with a named maintainer.** SECURITY.md routes reports through GitHub private vulnerability reporting, targets acknowledgement within 5 business days, and names a security maintainer (@kubet, Vukašin Kubet) who reviews security-sensitive changes; pull requests touching authentication, IAM, cryptography, or secrets request review from listed code owners.
- **Permission evals that grade ask-before-act behavior.** The `evals/` harness includes tasks named for the boundary itself: `ask-before-invite`, `permission-agent-access`, `secret-request`, `trigger-weekday-summary`, `memory-remember-forget`. The team grades whether its agents ask before inviting, granting, or touching secrets — our question, asked as a benchmark.
- **"A connector before a token."** A commit landed just before the first draft of this report (PR #12784, 16 November 2026) makes the rule explicit: an app with a connector is a sign-in, not a pasted API key. The setup flow now shows a sign-in row instead of asking the person to paste `LINEAR_API_KEY`. The API key remains only as a fallback when the person refuses the connector.
- **Agents propose, people approve, even for skills.** An agent may propose changes to its own skills — and a person approves them. The agent's self-modification path has a human gate.
- **Company as code.** Every agent, skill, rule, connector, and piece of context is a file in one git repo the company owns: versioned, reviewed, and extended like software. The harness itself is open source and self-hostable (VPC or on-prem, from the same images as the managed cloud).
- **Shipping pace.** Multiple commits a day; the `dev` branch shows PRs numbered to #13098 on 26 November 2026, against #12784 on 17 November — about 300 pull requests in nine days, including connector, gateway, and QualiLoop work.
- **Their own agents write code in the open.** Commits on the `dev` branch are authored by `agent-kortix` as well as by people, and the team's own intake agent triages every issue while worker agents fix it on their own machines. The team runs its own agents against its own repo, in public — the same work this report describes, done where anyone can watch it.

## 2. What it should never do alone

- **Never let triggers run without their code filters.** Schedules, webhooks, connector events, and app events start agents with nobody at the keyboard. The filter-in-code that drops noise before any model runs is the only thing between a noisy event source and expensive autonomous work at 3 a.m. A trigger without a filter is an open door.
- **Never run a workspace with no policy declared.** The project's own site says it plainly: a workspace with no policy declared runs every action. Allow, Ask, and Block are a thing you configure, not a thing you inherit — the guardrails exist, but the default is open. Writing the policy is the first act of adopting CompanyOS, before any agent touches a real connector.
- **Never let swarms run without budget caps.** Thousands of agents can run in parallel on one config, and every one of them burns model calls. The LLM gateway has budgets and access rules — the risk is misconfiguration, and swarms multiply any mistake by the number of agents running.
- **Never let an agent's self-proposed skill change take effect without the person's approval.** The mechanism exists and is the right one. The risk is approval fatigue at scale: a person who approves fifty skill changes a week will eventually approve the fifty-first without reading it.
- **Never paste API keys.** The team's own rule says connector-first. The API-key path remains as a fallback when the person refuses the connector — and fallbacks get used, especially under time pressure. Every pasted key is a credential the agent's environment can reach.
- **Never let the verifier session's verdict be the only record.** The verifier is also an agent. Who verifies the verifier — and where is its verdict recorded so that a person can check it later? A second agent is a check, not a guarantee.
- **Never merge an agent's change request without reading it.** Deny-by-default only works if the human actually reviews. A rubber-stamp approval is the same as no approval, and it is worse in one way: it carries a person's name.
- **Never adopt the white-label build without understanding the Platinum exclusivity.** The free white-label license requires Platinum as the exclusive compute provider for everything it offers. That is a business dependency, not a security issue — but it is a lock-in question worth asking before building on it.

## 3. Where the boundary is unclear

- **Whether the agent-to-agent hand-off chain is recorded in a form an outside party could verify.** The record itself exists on every plan — the project's site says recording is never gated — but reading, exporting, and streaming the audit trail out to your own SIEM is an Enterprise entitlement. On the lower plans the record exists but cannot leave the platform, so whether a non-Enterprise owner can hand a customer a verifiable hand-off chain is **unverified; worth asking.**
- **What happens when the acting agent and the verifier disagree.** The outcome loop says a separate verifier confirms completion. The disagreement path — who wins, and whether the person is told — is not described in the material we read — **unverified.**
- **Whether the "none means all" reading exists anywhere in production config.** The eval task `permission-agent-access` seeded an agent with `"secrets": "none"`, which the config sync read as *every* secret (fixed in PR #12782, 16 Nov 2026). The bug was in the eval harness, not production — but whether the same default-open reading exists anywhere a real agent's config is parsed is **unverified; worth asking.**
- **Cost per outcome.** Pricing is credits: free is $0 with 500 credits a month on the first workspace, and paid plans are a monthly credit pool. No per-outcome cost figure is stated in the material we read — **unverified.**
- **Old Suna docs still circulate.** Forks and mirrors of the old Suna README show an Apache-2.0 badge and the old self-hosting guide; the current LICENSE file is Elastic License 2.0. An adopter reading the old docs may misunderstand what they are allowed to do — **worth a note on the new README, not an accusation.**

## 4. Three questions for the maintainers

1. The audit trail exists on every plan, but exporting it to your own SIEM is an Enterprise entitlement. Can a non-Enterprise owner get the full hand-off chain — what was asked, what ran, what the verifier concluded — out of the platform in a form a customer could check?
2. When the acting agent and the verifier disagree about whether an outcome is done, who wins, and is the person told?
3. The `"secrets": "none"` seeding bug was caught in evals. Was the same default-open reading checked anywhere in production config parsing — and what now prevents a config value from silently meaning "all"?

## Three jobs it could take today

1. **Multi-step research-plus-data commission** — research a question, pull the data, and land the result as a change request a person approves; verifiable by the change request and the numbers.
2. **Public issue triage** — the team's own intake agent already triages every issue and worker agents fix it on their own machines; a public triage commission is the same work, done in the open; verifiable by the triaged issues.
3. **A scheduled multi-agent workflow with a verifiable outcome** — a goal with a definition of done, run by a swarm, confirmed by a verifier session; verifiable by the outcome record.

**Suggested first commission:** a multi-step research-plus-data commission, done in the open and written to the ledger.
