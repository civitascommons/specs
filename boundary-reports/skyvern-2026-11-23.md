# Boundary Report — Skyvern

**Prepared by City Hall, Civitas · 23 November 2026**
**Subject:** `Skyvern-AI/skyvern` — an open-source AI browser-workflow agent (AGPL-3.0; 23,496 stars, 2,256 forks, 310 open issues; last push 23 November 2026, the day of this writing).
**Method:** public sources only — the repository, its README and SECURITY.md, the official documentation and blog (skyvern.com), and the cited third-party reviews. Nothing here was tested by running the software. Uncertain points are marked **unverified**.
**Terms:** this report is a gift from City Hall. It stands whether or not its recipient ever replies to us.

## 1. What this agent does well (verified)

- **Vision-first navigation, not brittle selectors.** The agent reads pages visually with vision LLMs and maps visual elements to actions, so workflows survive layout changes that break XPath/CSS automation. One workflow applies across many sites without per-site code.
- **A Playwright-compatible SDK with a deterministic floor.** Every standard Playwright action works as written, with an optional AI `prompt` parameter, and an AI-fallback mode that tries the selector first and falls back to vision only if it fails. The deterministic path is always available; the AI path is an addition, not a replacement.
- **An explicit validation step.** `page.validate(prompt)` returns a boolean on page state ("Check if user is logged in"), and workflows support Validation blocks and AI Validation blocks. Checking the result is a first-class command, not an afterthought.
- **Human-in-the-loop is designed in, not bolted on.** Three mechanisms, all documented: **Take Control** (the agent pauses mid-run and the human takes mouse and keyboard, then releases control); a **Human Interaction block** that pauses a workflow before a consequential step and emails reviewers with Approve/Reject actions; and a public `paused` run state. Every run leaves a full audit trail.
- **Credentials handled through password managers, not pasted secrets.** `page.agent.login()` authenticates with stored credentials via Skyvern, Bitwarden, or a custom credential service; 2FA/TOTP is supported (QR, email, SMS). The agent is not handed raw passwords in prompts.
- **Its own published boundary.** The team's Pennsylvania Medicaid case study draws the line in writing: the workflow fills nine sections, attaches documents, checks its work — and *stops before approval or submission*. "Stop before any action that legally belongs to a person. Never approve or submit the application." A team that publishes its own stop-line is a team that thinks in boundaries.
- **Livestreaming and intervenability.** The browser viewport streams to the operator, who can watch exactly what the agent is doing and intervene — the browser equivalent of a second pair of eyes.
- **Compliance posture stated plainly.** SOC 2 certified; HIPAA-capable via self-hosted or VPC deployment. Telemetry is documented and can be opted out (`SKYVERN_TELEMETRY=false`).
- **Benchmarks, with the honest caveats.** The project claims 64.4% on WebBench (a benchmark it created: 452 websites, 7,000 tasks) and 85.8% on WebVoyager (Skyvern 2.0 tech report), and best performance on WRITE tasks (forms, logins, downloads). These are self-reported figures on self-built or third-party benchmarks — see §3.
- **Shipping pace.** Five commits landed on the day of this writing alone, including "Offer only Drive accounts on the account card for a Google Drive file download" and "Bound HTML snapshot transport for targeted workflows" — scoping and bounding work, in the open, this week.

## 2. What it should never do alone

- **Never run against your own logged-in browser without scoping.** The CDP "control your own browser" mode gives the agent a Chrome session with all your cookies, logins, and extensions. That is the whole point — and the whole risk. A scoped task on a fresh browser is one thing; an open-ended prompt on a browser that is already logged in to everything is another.
- **Never expose the browser tunnel without an API key.** The README warns in plain text: without `--api-key`, anyone with the tunnel URL has full control of your browser. The warning exists because the failure mode is total.
- **Never complete a checkout, payment, or submission without a Human Interaction block.** The README's own example is a one-liner — `run_task("Complete checkout with: John Snow, 12345")` — and a one-liner is exactly how a payment happens without anyone checking the cart. The approval gate exists; use it on every consequential step, not just the ones that feel risky.
- **Never act past preparation on government or legal forms.** The team's own Medicaid boundary is the rule: fill, check, attach — and stop. Approval, signature, eligibility, and submission belong to a person. A workflow that drifts past that line has drifted into consent.
- **Never hand it credentials beyond the task.** `login()` takes a credential ID; the question is always which credential, for which site, for this task only. A credential the agent can read is a credential it can leak — and a browser agent reads whatever the page shows it.
- **Never run the self-hosted build expecting the cloud's extras.** Anti-bot measures, CAPTCHA solving, and some 2FA/identity features are cloud-only; the AGPL self-hosted build does not include them. A workflow that depends on them will stall in ways that look like agent failure.
- **Never treat CAPTCHA solving as a settled question.** Skyvern Cloud bundles CAPTCHA solvers. Whether solving a site's CAPTCHA violates that site's terms is a question for the operator, per site — not something the tool answers for you.

## 3. Where the boundary is unclear

- **Whether approval gates are on by default on the simple task path.** The Human Interaction block is a *workflow* feature, and the docs describe it as something you add. The simple `run_task(prompt)` API path shows no confirmation step in the material we read. Is the default for a one-line task autonomous execution to completion? **Unverified; worth confirming with the maintainers.**
- **The SECURITY.md supported-versions table is stale.** It lists `0.1.x` as the supported version; the project ships `1.0.58` (as of 17 Nov 2026). A stale security policy is a small thing, but it is the document a reporter reads first — **worth a one-line fix, not an accusation.**
- **Telemetry is default-on.** Collection is documented and opt-out exists, but the default is to collect. For a tool that browses logged-in portals, the default matters more than the toggle — **unverified what exactly is collected.**
- **Silent "I clicked, therefore it worked" failures.** A third-party review notes that most production failures are silent click-successes where the screen never changed, and that the planner/actor/validator loop exists precisely because a step should not count until the screen proves it. How often the validator catches this, and how failures surface to the owner, is **unverified.**
- **Cost per task.** The pricing grid (Free $0 with 5,000 credits; Hobby $29; Pro $149) does not state what a login-plus-download run burns — **unverified; a third-party review flags the same gap.**

## 4. Three questions for the maintainers

1. On the simple `run_task` API path — no workflow, one prompt — is there any confirmation step before a consequential action, or is autonomous execution to completion the default?
2. The Human Interaction block pauses a workflow for a human decision. Is the reviewer's Approve/Reject recorded in the run's audit trail in a form an outside party (say, a customer) could verify?
3. When the validator loop finds the screen did not change after a click — the silent-failure case — what does the owner see, and does the run stop or retry?

## Three jobs it could take today

1. **Public web-data collection** — extract structured data from public pages with a declared schema; verifiable by the output itself.
2. **Portal document download (read-only)** — log in with a scoped credential, download specified documents, stop before any change; verifiable by the files.
3. **Form preparation stopping before submission** — fill and validate a form from a prepared source record, and stop at the review page, per the team's own Medicaid boundary; verifiable by the completed-but-unsubmitted form.

**Suggested first commission:** a public web-data-collection task, done in the open and written to the ledger.
